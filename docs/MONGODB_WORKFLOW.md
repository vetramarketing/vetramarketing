# MongoDB integration plan

The app is currently browser-local. **No MongoDB connection, API, sign-in, cloud sync, or upload of browser data is active.** The remote-first repository adapter is prepared, but it is not connected to the UI until authenticated API details and a reviewed migration are available. This document defines the data and behavior to preserve at that point.

## Data to carry forward

- `vetra-marketing.workspace.v12` is the active browser key. Its JSON contains companies, business types, customers, products, optional Cloudinary metadata, groups, destinations, posts, console scripts, and Trash. `src/lib/workspace-storage.ts` serializes and migrates it; `src/lib/data.ts`, `customer-data.ts`, and `console-scripts.ts` validate it. The in-memory `Workspace.version` is `1`, while the persisted format version is `12`. Legacy store fields become company fields without changing IDs; prior keys remain available for recovery. The separate key prevents an older open tab from overwriting the new order and customer fields during normalization.
- Persist only the current post fields. Removed title, content, status, planned-date, and dated measurement fields are not new database columns. Keep Facebook IDs as strings so long IDs retain every digit. Preserve the publication timestamp and nullable Viewers total; a later update replaces that total.
- `vetra-marketing.locale` is a browser preference. It can remain local until a user preference API exists; then it should be scoped to the signed-in user, separately from workspace records.
- `vetra-marketing.post-clicks.v1` stores per-post link clicks for the current Bangkok day in this browser. These counts reset daily and are intentionally separate from workspace records, JSON backups, CSV, and the future MongoDB migration unless the user requests shared click reporting later.
- `src/lib/facebook-group-directory.json` is supplied reference data for Group ID to name lookup. It is a seed/catalog, not a browser workspace or a live Facebook lookup. Existing workspace group names edited by users take precedence over catalog names.
- The earlier v1–v8 browser keys are recovery copies. They may include unpublished records or measurement history excluded from the current format. Never silently promote unpublished records into the published-post monitor. v5/v6 catalog records are preserved intact. Older companies receive empty logo/owner values and index-based sort order; original names, IDs, initials, colors, descriptions, and post references are preserved. A v6 post receives `productId` only when its saved product name matches exactly one catalog record; ambiguous names retain their text without a link.

## Simple product and company models

| Collection  | Editable fields                                                    | Internal fields                                                                                   |
| ----------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `products`  | `name`, `imageUrl`, `companyIds`, `sortOrder`                      | stable string `id`, authorized `workspaceId`, optional `deletedAt`                                |
| `companies` | `name`, `businessTypeId`, `logoImageUrl`, `ownerName`, `sortOrder` | stable string `id`, authorized `workspaceId`; preserved legacy `initials`, `color`, `description` |

Product names are required, up to 200 characters. Company names are required, up to 100 characters; owner names are optional, up to 100. Image URLs are optional empty strings, HTTPS links up to 2,048 characters without embedded credentials, or exact bundled paths approved in `src/lib/catalog-images.ts`. Bundle those files with each deployment or explicitly migrate them to hosted images. Arbitrary local paths are rejected. Sort order is a whole number from 0 to 1,000,000. Display ascending by `sortOrder`, then by string `id` using simple collation. Names and sort numbers need not be unique. Current limits are 10,000 products and 100 companies.

The optional workspace-level `appliedDataUpdates` array records one-time supplied additions. Preserve it in API snapshots, migration, and backups so deleted or renamed supplied products are not automatically recreated.

Products may carry `imageAsset` and companies `logoAsset` with verified Cloudinary identity/dimension metadata. The URL remains the display field. The optional `CatalogSaveRequest.imageUpload` token lets the server bind a staged upload to one authenticated catalog save; do not accept client-submitted metadata as ownership proof. Preserve metadata and media references for Trash. See [Cloudinary workflow](CLOUDINARY_WORKFLOW.md) for upload, retry, and cleanup integration. Cloudinary and MongoDB connections remain inactive.

Products can explicitly link to several companies through `companyIds`. Legacy associations can be derived from explicit post links until reviewed. Product suggestions and name matching use the post's company; existing explicit product IDs remain intact. A post stores both the stable `productId` and its original `product` name snapshot.

Business types and customers use separate workspace-scoped collections. `src/lib/mongodb-customers.ts` prepares validated documents and indexes; `docs/COMPANIES_AND_CUSTOMERS.md` describes the extensible field structure. A company has a `businessTypeId`; each customer has a `companyId`. Preserve nested social links, domains, GitHub identities, custom field IDs/values, timestamps, and archived field definitions. Domain expiry and last-contact dates are date-only strings, not BSON instants. Customer identity/contact fields are not public metadata.

`src/lib/mongodb-catalog.ts` provides `ProductDocument`, `CompanyDocument`, field-only create/update inputs, `CatalogSaveRequest`, and `CATALOG_INDEXES`. `prepareCatalogDocuments(workspace, authorizedWorkspaceId)` validates and creates detached document arrays, including Trash and legacy branding. It makes no network calls. The API must supply the workspace ID after checking membership; this helper is not authorization. MongoDB may create its own `_id`; keep the app's `id` unchanged for references and import retries.

The prepared compound identity indexes enforce uniqueness of `(workspaceId, id)` per collection. Sorting indexes cover workspace and display order; product queries include `deletedAt: null` for active records. Review existing duplicate IDs before index creation. MongoDB documents [compound uniqueness and existing-data restrictions](https://www.mongodb.com/docs/manual/core/index-unique/).

### API wiring when provided

1. List products and companies through authenticated, workspace-scoped, paginated reads. Return the workspace revision alongside records. Render the same local forms and image placeholders.
2. Submit only the relevant input fields and stable ID, plus `expectedRevision` and `operationId`. Create companies with generated initials, the default color `#263b4b`, and an empty description; preserve those legacy fields on edits. Validate the resulting candidate with the shared domain rules on the server, including the collection limits. Never spread an untrusted request directly into a MongoDB update.
3. In one transaction, verify/increment the workspace revision, write the entity, and record the operation outcome. Reject stale revisions with `409`. A retry of the same operation and payload returns its previous result; reusing the key for different data is rejected. MongoDB's [atomicity guidance](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/) explains conditional updates and multi-document transactions.
4. Product Delete sets a server timestamp in `deletedAt`; Restore clears it within 30 days. Expiry removes only the catalog record, leaving post text intact. Preserve the ISO timestamp representation in API/JSON; map to BSON Date explicitly if the server uses dates internally. Company deletion is not exposed because companies own groups and posts.
5. Return the validated record and new revision. Keep edits visible on failure. Wire the remote adapter only when real endpoints, authentication, and conflict behavior are available; do not silently fall back to local writes after remote errors.

## Storage boundary and API contract

The UI now uses the typed, asynchronous boundary in `src/lib/workspace-repository.ts`. Its browser provider loads a validated snapshot and revision and commits changes with an expected revision and operation ID. It keeps the old browser keys as recovery copies. Browser storage cannot guarantee atomic compare-and-swap across tabs; the API provider must enforce revisions in a database transaction. This whole-workspace commit boundary is transitional: a production API should send entity-scoped operations or a bounded change set, not upload and replace the entire workspace for each edit. Adapt the repository contract when the API shape is known. A conflicting API write should return `409` with the latest revision so the UI can reload and let the user review unsaved edits. Do not turn a network failure into a success message.

`src/lib/remote-workspace-repository.ts` is the prepared dual-storage adapter. The app's `createBrowserWorkspaceRepository()` factory currently selects the local provider; supply an authenticated remote source to switch it after migration. That source must implement `load`, `commit`, `recover`, and `subscribe`, and provide the signed-in user ID and authorized workspace ID for a separate `vetra-marketing.remote-cache.v1.*` browser key. A successful remote load/save updates that cache, including each post's `pinned` flag. Remote failure is reported as failure and never writes to the cache or the existing `vetra-marketing.workspace.v12` key. Cache-write failure does not reclassify a confirmed database save as failed; surface its `onCacheError` warning in the eventual UI. `readCachedSnapshot()` is only for an explicit read-only recovery view, never an editable offline fallback. Locale and legacy recovery copies remain in their existing browser keys. Scope the cache from authenticated identity, clear it appropriately on sign-out/account removal, and do not enable this adapter or auto-import local posts before the migration steps below are complete.

The eventual server must authenticate every request and derive workspace/tenant scope from that identity; it must not trust a client-supplied workspace ID as authorization. Validate all incoming records server-side with the same domain rules, enforce size limits, and return only data the user can access. Keep MongoDB credentials and any future social credentials on the server. No connection string or token belongs in browser code or a committed environment file.

Use separate workspace-scoped records or collections for workspace metadata, companies, business types, customers, products, groups, destinations, and posts. Only posts have the nullable Viewers total and boolean `pinned` flag; default missing legacy flags to `false`. A whole workspace can exceed MongoDB's single-document limit at the current validation maximum, so do not store all posts as one document. Preserve stable application IDs, `productId`, `destinationId`, and legacy `groupId` references. Group destinations mirror the existing group catalog. Page/account destinations are created from links only when the publishing account is identifiable; ambiguous links remain unlinked. Index workspace-scoped IDs and normalized post identities, including posts in Trash, and lead company feeds with pinned posts. The external-identity index is initially nonunique because older data may contain duplicate pairs; the API must reject new pairs transactionally while preserving historical collisions for review. Index Facebook Group IDs for lookup, but do not add a universal unique index yet: legacy/sample groups may have blank IDs, and current local data may contain an active and a trashed group with the same numeric ID. A post save that creates its group, a CSV import, and a group deletion that changes post links must be atomic. Conditional writes need server-side revision checks, not a client read followed by an unconditional replacement. `src/lib/mongodb-posts.ts` prepares detached post/destination documents and index declarations without making a network call.

Soft-delete customers, products, posts, and groups with `deletedAt`. Keep them restorable for 30 days. Run expiry using server time after the retention period; before permanently removing a group, preserve any linked post's usable URL and clear or update its group reference as the current `pruneTrash` behavior does. Do not use an independent group TTL deletion that can strand posts. Keep restore and backup behavior available in the API-backed UI.

## Migration when the API is ready

1. Let the user preview counts and download a v9 JSON backup of the current browser workspace, including catalog records, optional asset metadata, Trash, and current Viewers totals. Treat `serializeWorkspace`/`deserializeWorkspace` round-tripping as the compatibility check.
2. Once authenticated, import the active v9 data under the correct workspace with an idempotency key. Validate and compare IDs, image URLs, media metadata, owner names, sort order, links, current totals, product/destination/group references, and existing external-identity collisions before accepting it. Verify any Cloudinary ownership separately before recording managed references or permitting cleanup. Handle collisions as reviewable conflicts; do not overwrite remote work automatically. Keep static catalog entries separate from user-owned groups.
3. Read the imported snapshot back from the API and verify it against the preview. Only after confirmed success should the UI switch that workspace to API persistence. Retain the browser copy and downloaded backup for recovery; do not silently upload, erase, or replace local data.

Before enabling the API provider, test cross-user isolation, concurrent edits, retries after uncertain network outcomes, duplicate IDs/links including Trash, atomic post-and-group saves, large imports, 30-day restore/expiry, and JSON/CSV round trips. Keep the existing browser flow until those checks pass.
